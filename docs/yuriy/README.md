# Печать и уведомления ДокМаршрута

Ветка `yuriy`. За основу взята `origin/denis` (`fe44295`), которая включает сборку `damir`. На момент начала работы ветки `main` на сервере не было.

## Карточки 20–23

- **20. Настройки почты.** В разделе «Сервис» откройте «Настройки почты», заполните сервер, порт, таймаут, SSL, отправителя и при необходимости логин и пароль приложения. «Проверить отправку» сохраняет настройки и отправляет письмо на адрес отправителя. Пустое поле пароля оставляет прежнее значение, сохранённое значение не выгружается обратно в форму. Тестовая попытка попадает в журнал.
- **21. Печатная форма.** `ПечатьДокументов.СформироватьТабличныйДокумент(ДокументСсылка)` возвращает заполненный табличный документ. Макет включает шапку, участников, поля в порядке настройки вида, этапы с решениями текущего цикла и подвал. Скрытые поля не печатаются. В интеграционной сборке описание полей берётся из табличной части `Вид.Поля`, поскольку экспорт `КонструкторВидов.ПоляВида` в `denis` отсутствует.
- **22. Письмо с вложением.** `СформироватьPDF` возвращает двоичные данные из потока в памяти. Для карточки документа сохранён существующий интерфейс `СформироватьВложениеПечатнойФормы`. Учебная лицензия блокирует сохранение табличного документа в PDF, при таком ограничении используется HTML с теми же данными. Согласование после записи вызывает существующую `ОтправитьПоСобытию`, которая передаёт управление `ПриСменеСтатуса`. Адреса берутся у ответственного и его руководителя, повторяющиеся адреса исключаются. В файловой базе отправка синхронная, в клиент-серверной запускается фоновое задание.
- **23. Ошибки почты.** В журнале уведомлений включите отбор «Только ошибки». Каждая попытка получает отдельный идентификатор, ошибки также идут в журнал регистрации. Сохранённый статус документа не зависит от ответа SMTP. Порт и таймаут задаются константами через форму.

## Что проверено

- `py -X utf8 tools/check_dump.py` и `py -X utf8 -m unittest discover -s tools/tests -v`.
- XML загружен в отдельную учебную файловую ИБ 8.3.27.1508. Для этой проверки в копии заменён только параметр интерфейса 8.5, которого нет в 8.3. Конфигуратор обновил схему, проверка серверных модулей и тонкого клиента завершилась без ошибок.
- В режиме Предприятия сформированы табличные документы для шести записей трёх демо-видов. Учебная платформа вернула HTML-вложения из-за ограничения экспорта PDF.
- На локальном SMTP-сервере с тестовыми адресами проверены отказ соединения и отказ аутентификации `535`. При отказе аутентификации после записи статуса «Согласован» в журнале были отдельные ошибки ответственного и руководителя. После замены пароля оба адресата получили HTML-письма с вложением и статусом «Согласован».

Для приёмки нужен прогон на целевой платформе с доступным экспортом PDF, реальные тестовые ящики и проверка клиент-серверного режима. Адреса, пароли приложения и токены храните вне Git. После успешного прогона можно записать резервное видео для карточки 24.

## Карточка 26. Повторная отправка

1. После обновления конфигурации вызовите ошибку SMTP при отправке документа с настроенными получателями. В «Журнале уведомлений» включите «Только ошибки».
2. Исправьте параметры SMTP. В журнале выберите нужную строку и нажмите «Отправить повторно». Повтор использует адрес из этой строки, исходную тему, текст и вложение. Старая строка остаётся в журнале, результат добавляется отдельной строкой с новым номером попытки.
3. Для автоматического повтора администратор включает флажок «Автоматически повторять неудачные отправки» в настройках почты и сохраняет форму. Регламентное задание проверяет очередь каждые пять минут и делает до двух автоматических повторов на письмо. Флажок можно снять в той же форме.

Очередь формируется из неудачных писем документов, отправленных после обновления. Для старых записей, проверочных SMTP-писем и ошибок формирования вложений исходного письма в очереди нет. При аварийном завершении сеанса посреди повтора запись остаётся помеченной как выполняющаяся. Перед разбором такой записи администратору нужно проверить, принял ли письмо SMTP-сервер.

На учебной 1С и локальном SMTP проверены отказ `535`, исправление пароля, ручной повтор для руководителя и обработка очереди для ответственного. Обе доставки записались как попытка №2. Повторный запуск по уже обработанной строке дубликат не отправил. Включение и выключение расписания проверены отдельно.

## Карточка 27. Система взаимодействия 1С

При смене статуса в зарегистрированной базе ответственный и его руководитель получают личное сообщение с номером документа, сохранённым статусом, этапом и навигационной ссылкой. Получатели определяются по полю «Имя пользователя ИБ» в карточке сотрудника. Одинаковые получатели объединяются. Перед отправкой проверяется состав участников обсуждения. Результат записывается в журнал с каналом «Система взаимодействия». Почта обрабатывается отдельно, в очередь автоповтора попадают только SMTP-письма.

Для приёмки зарегистрируйте тестовую ИБ в Системе взаимодействия. Укажите логины тестовых пользователей ИБ у ответственного и руководителя, войдите под этими пользователями в клиент 1С и подключите их к Системе взаимодействия. Из сеанса согласующего измените статус документа. Проверьте личное сообщение в клиентах получателей и записи об отправке в «Журнале уведомлений». С пустым логином одного сотрудника журнал должен показать ошибку привязки, а остальные получатели и почта должны по-прежнему обрабатываться.

В отдельной учебной ИБ прошли загрузка метаданных и проверка Конфигуратора. Проверены формирование текста и ссылки, обработка пустой привязки, отклонение обсуждения с посторонним участником и запись нового канала в журнал. На незарегистрированной ИБ подтверждена работа SMTP и очереди. Скрытие одного поля вида уменьшило табличный документ ровно на одну строку. Получение живого сообщения в клиенте 1С требует зарегистрированной ИБ и тестовых пользователей.
